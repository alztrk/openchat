# OpenChat

<p align="center">
  <img src="brand/variants/openchat-horizontal.svg" alt="OpenChat" width="560" />
</p>

OpenChat is a cross-platform AI chat app. It aims to give people one focused place to talk with hosted AI services and, over time, models running on their own devices. People will be able to choose an available model, have a conversation, and return to their chat history from the same app.

## Why OpenChat

AI models are accessed through different services, accounts, and local runtimes. OpenChat aims to bring those options into one chat experience, with a clear choice of model and support for the connection methods available for each integration.

## Product goals

- **One place for AI conversations:** Build a clear chat experience that can grow to support multiple hosted and local models.
- **Choice of model:** Let people select from the models available through their configured connections.
- **Conversation history:** Make previous chats available to return to.
- **Flexible connections:** Integrate both OAuth and API key connection methods, where supported by an integration.
- **Responsive performance:** Keep the app responsive as conversations and supported platforms grow.
- **Multiple platforms:** Start on Windows, with a path toward Linux, macOS, Android, and iOS.

## First release

The first release is planned as a Windows chat app. ChatGPT and OpenCode are the starting integrations, with additional API-key providers available as their account connections are configured. The initial scope is:

- Start and continue AI conversations.
- Choose an available model from a configured provider.
- Browse and reopen conversation history.
- Connect through the available OAuth or API key method.

This release focuses on conversations and includes local workspace and terminal tools. Their execution and permission boundaries are described under Current status.

## Roadmap

See [ROADMAP.md](ROADMAP.md) for the current implementation status, ordered next steps, and longer-term provider and platform plans. It distinguishes shipped code from work that still needs validation or implementation.

## First-release boundaries

- Chat is the product focus.
- Local file and terminal tools run with the current Windows user's permissions. `Ask for approval` prompts for each supported call; `Full access` skips prompts. File path restrictions do not sandbox terminal processes.
- Windows is the only first-release platform target.

## Current status

Before opening the service or applying schema changes, Windows startup runs SQLite's read-only quick integrity check. A damaged database is left untouched and is not retried as a transient failure. Schema migrations require a verified SQLite online backup in `%LOCALAPPDATA%\OpenChat\db\backups\`; the backup includes committed WAL data.

The Windows chat database is shared by the Flutter/Drift UI and the Rust service in WAL mode. Both SQLite runtimes must remain at version 3.51.3 or newer: earlier versions have an upstream WAL-reset race that can corrupt a database when separate connections write or checkpoint concurrently. Tests assert the minimum version for both bundled runtimes.

The Windows app uses Flutter for the interface and a local Rust service for ChatGPT OAuth, account and workspace selection, model and quota reads, and streaming Responses. When a selected model returns a reasoning summary, OpenChat stores and displays that summary separately from the answer; the raw hidden reasoning is not exposed by the API. OAuth tokens are stored as byte blobs in Windows Credential Manager within its per-credential size limit. Conversations, messages, project names, favorite models, and project folders are stored locally in `%LOCALAPPDATA%\OpenChat\db\openchat.sqlite3`, with logs and cache directories under `%LOCALAPPDATA%\OpenChat\`. Startup retries transient local storage or service failures for up to three attempts; the chat sidebar offers a retry if initialization still fails. Startup phase, attempt, safe error codes, and SQLite failure categories are written to `%LOCALAPPDATA%\OpenChat\logs\openchat-app.log`. They exclude SQL statements, bound values, paths, tokens, and conversation data. Windows allows one OpenChat UI process at a time. Drift applies schema changes and the matching SQLite `user_version` in one transaction, rechecking the version after acquiring SQLite's write lock. Sanitized OAuth, model catalog, usage, and local-runtime diagnostics are written to `%LOCALAPPDATA%\OpenChat\logs\openchat-service.log`; they include safe error codes, HTTP statuses, durations, and item counts while excluding callback parameters, response bodies, tokens, account details, model paths, and prompts. The service log is limited to 1 MiB and is cleared before writing the next entry when that limit would be exceeded. Filesystem, web search, URL reading, and terminal tools are included with model requests; the model chooses whether to call them. Settings offers `Ask for approval` and `Full access`; `Ask for approval` is the default, asks once per supported file-tool call, and confines canonical paths to the attached project folder or `%LOCALAPPDATA%\OpenChat`. `Full access` skips prompts and permits the same listing, search, read, file-information, write, and edit tools to operate anywhere. The execute_command and send_terminal_input tools are also model-callable. Terminal operations require per-call approval in `Ask for approval`; `Full access` skips that prompt. Commands run as the current Windows user from the project root, or the OpenChat data root when no project is attached. File path restrictions do not sandbox terminal processes. The model catalog compatibility version is `0.157.0`, tracked independently of OpenChat's product version and aligned with the Codex `client_version` query parameter. The integration follows the public Codex OAuth client configuration and private ChatGPT endpoints; provider compatibility can change and requires a real account sign-in to confirm.

The interface uses a semantic blue-and-neutral palette in light and dark themes, shared dropdown/select controls, and English, Turkish, German, Spanish, and French localization. AI question prompts are stored as resumable run state, surfaced in the active conversation, and paired with Windows notifications. ChatGPT OAuth and ChatGPT API-key conversations can request image generation through the `generate_image` tool; image input support remains a separate model capability. Generated files are stored as local chat attachments. See [AI image generation](docs/ai-image-generation.md) for authentication boundaries and limitations, and [workspace tools](docs/tools.md) for question persistence and recovery behavior.

Data from earlier installations is not imported automatically. OpenChat reads app state only from `%LOCALAPPDATA%\OpenChat`.

When running the native service directly, `--data-root <absolute-path>` selects a separate database, log, and cache root for that process. The normal desktop app does not pass this option and continues to use `%LOCALAPPDATA%\OpenChat`. Windows Credential Manager credentials are shared across data roots.

Before each ChatGPT request, OpenChat checks the access token's JWT expiration and refreshes it when it is within five minutes. An unexpected `401` still triggers a refresh and one retry.

OpenCode Console is available as a chat provider. OpenChat caches the model catalogs for six hours; an explicit refresh bypasses the cache, and an expired catalog remains available as stale data after a network or temporary server failure. Authentication and request errors are shown instead of being hidden by stale data. ChatGPT catalogs are scoped to an account and workspace. The OpenCode integration supports Zen's OpenAI-compatible Chat Completions endpoint and its Responses endpoint for models marked as compatible in the model catalog. Paid models require an OpenCode Console service API key, stored with the platform secure-storage plugin, and are billed per request by OpenCode. Anthropic Messages, Gemini, and System One protocol families are not supported by this OpenCode integration. See [OpenCode's inference documentation](https://opencode.ai/v2/docs/console/inference/) and [model list and pricing](https://opencode.ai/v2/docs/console/models/) for current endpoint and billing details.

Gemini, Groq, Cerebras, OpenRouter, and Mistral are available through their official OpenAI-compatible chat APIs. Their API keys are stored by the platform secure-storage plugin. Provider model catalogs are cached for six hours per provider and key; the cache stores only a SHA-256 key hash with model metadata. Gemini, Groq, Cerebras, and Mistral show the models their authenticated catalogs return, so model price and quota depend on the provider account. OpenRouter shows only text-chat models whose current catalog reports zero input and output prices and tool support. Mistral's catalog filters archived and non-chat models, reads context limits and vision support from the model API, and supports reasoning controls on the models documented by Mistral. Gemini's unpaid API tier may use submitted content to improve Google products; its connection card shows this before a key is added. These integrations still need verification with real provider accounts.

Local inference engine release catalogs are embedded in the service. OpenChat currently exposes a verified llama.cpp preview for managed installation on Windows x64, with CPU and NVIDIA CUDA packages. vLLM and ExLlama are deprecated on Windows, where new managed installations are disabled; existing runtime files and model registrations are preserved. vLLM is available as a hash-locked Linux x64 CUDA 13 runtime with pinned Python dependencies. ExLlamaV3 is available for managed installation on Linux x64 with NVIDIA CUDA 12.8, using a pinned TabbyAPI source commit, hash-verified runtime assets, and platform-specific Python lockfiles. The managed vLLM and ExLlama installation and inference paths still need live validation on supported CUDA hosts. Engine binaries are stored under `%LOCALAPPDATA%\OpenChat\runtimes` rather than bundled into the app executable. In Settings, users can choose and persist a separate model folder for each engine. Choosing or resetting a folder starts a bounded scan: llama.cpp folders are searched for GGUF files, while vLLM and ExLlama folders are searched for Transformers model directories containing a configuration and weight file. OpenChat lists unregistered matches and asks before registering them; users can also scan again manually. Changing a folder does not move existing registrations. Model-catalog downloads and manual copy or move actions use the selected engine folder, while keep leaves a manually added model in place. The default folders are `%LOCALAPPDATA%\OpenChat\models\llama`, `%LOCALAPPDATA%\OpenChat\models\exllama`, and `%LOCALAPPDATA%\OpenChat\models\vllm`. Windows x64 llama.cpp can start a registered GGUF automatically when it is selected for chat, wait for `/health`, and stream chat completions through the shared conversation route. Startup cancellation stops only the process being started. Each managed llama.cpp model runs in its own process, so starting or stopping one model leaves other models running. Settings can stop models individually, and service shutdown stops all managed processes. Startup, timeout, inference, and runtime-disconnect failures are shown in the assistant response card. The runtime binds only to `127.0.0.1`. The app-service path has been exercised with a real GGUF through registration, streamed chat, response persistence, runtime stop, and service shutdown in an isolated profile. CPU verification used the official llama.cpp CPU archive with a real GGUF and matching vision projector; the server loaded the model and generated text tokens. CUDA verification used the installed CUDA build: it reported the RTX 3060, loaded CUDA libraries, generated the expected text answer for a simple arithmetic prompt, and identified a red square in an attached PNG. These were manual runtime checks, not automated release tests. CUDA packages are offered only when `nvidia-smi` returns a valid driver version at or above the release catalog's compatibility minimum; the recommended package also accounts for NVIDIA's corresponding driver release. The compatibility floors follow NVIDIA's [minor-version compatibility guide](https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html) and [CUDA release notes](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html). For llama.cpp models, OpenChat reads the declared context window from GGUF metadata and the active context and reported template capabilities from the loopback runtime `/props` endpoint; automatic compaction uses the active context. For image input, OpenChat pairs a GGUF with its exact-name adjacent `mmproj` projector, or with the sole projector in the same folder, and passes that file to llama.cpp. Copying or moving a registered vision model keeps the projector beside it. Ambiguous projectors are not paired, and the running server's `/props` response remains the source of truth for image capability. Release catalogs are tied to upstream repositories: [llama.cpp](https://github.com/ggml-org/llama.cpp/releases), [vLLM](https://github.com/vllm-project/vllm/releases), and [ExLlamaV3](https://github.com/turboderp-org/exllamav3/releases).

OpenCode's model endpoint supplies the available model IDs. Exact-ID matches in [Models.dev's OpenCode catalog](https://models.dev/) supply display names, descriptions, and context-window values. This metadata shares the six-hour catalog cache; if its source is unavailable, cached values are marked stale when available, while models remain selectable without metadata when no cached details exist.

OpenCode reasoning controls follow the model catalog's supported effort values. OpenAI-compatible reasoning selections are sent as `reasoning_effort`; models without request-time controls use their provider default.

On Windows, Settings > Local engines offers two independent llama.cpp paths. A user can select an existing `llama-server.exe`, which OpenChat uses to launch registered GGUF models without downloading a managed runtime. Separately, OpenChat can detect a running `llama-server.exe` with a loopback listener and asks before connecting. Setup checks `/health`, reads `/v1/models`, and uses `/props` when available; chat requests go to `/v1/chat/completions`. Multiple detected user-started llama-server processes can be connected at once. Each server and its models appear in a separate chat model-picker section, and chat requests are routed to the server that supplied the selected model. Connected external models are not registered as downloaded models. Disconnecting clears only that server connection; OpenChat never stops a user-started server. Connections are held by the running service and must be accepted again after it restarts. Servers that require authentication are not connected because OpenChat does not read credentials from other processes.

New conversations use one provider and model picker. ChatGPT, OpenCode, Gemini, Groq, Cerebras, OpenRouter, and saved favorites appear in its provider panel. API-key providers stay disabled until a key is connected. A favorite can be selected from another provider to switch the new conversation to that provider.

Shared instructions are saved locally in Settings and sent with each chat request. The Rust service converts requests and events to OpenChat's shared chat, tool, and stream-event types, then each adapter maps those types to the provider's native request and response format. ChatGPT receives instructions through the Responses `instructions` field; OpenCode and the four OpenAI-compatible APIs receive them as a Chat Completions `system` message. Provider-native payloads stay inside the service and do not cross the Flutter RPC boundary. Local file, web search, URL reading, and terminal tool definitions are sent with chat requests and run in the local Rust service. In `Ask for approval`, each supported call pauses until the user allows or denies it, and the backend independently restricts access to the project folder or `%LOCALAPPDATA%\OpenChat`; in `Full access`, those prompts are skipped and listing, search, read, file-information, write, and edit tools can access any folder. The execute_command and send_terminal_input tools are also model-callable. Terminal operations require per-call approval in `Ask for approval`; `Full access` skips that prompt. Commands run as the current Windows user from the project root, or the OpenChat data root when no project is attached. File path restrictions do not sandbox terminal processes. Tool activity, approval state, arguments, and results are saved with local conversation history. Tool calls are limited to six rounds, sixteen calls, and 16 KiB of arguments per call. Provider tool support still needs live verification for each selected model.

Conversation history remains intact in the local database, including completed tool calls and their results. New tool activities record their round and assistant-text position so ChatGPT and OpenAI-compatible providers receive the historical exchange in order; older activity records remain readable but lack that ordering metadata. Tool arguments and results are also included in compaction summaries and a separate per-conversation SQLite FTS5 index. The dedicated `targetPath` display field is omitted from provider history and the archive index; paths included in tool arguments or results remain part of the stored activity. Provider metadata keeps the model's context window visible in the selector. When metadata also reports a distinct input-token limit, OpenChat uses that limit for compaction and final request checks; otherwise it uses the context window. Compaction begins as usage approaches 80% of the active request limit. ChatGPT OAuth requests a Codex Responses compaction checkpoint. Before sending that checkpoint request, OpenChat caps its estimated token use at 75% of the known context window and shortens older tool-output strings in the request copy as needed. The complete tool results remain in the local archive and stay available to keyword retrieval. If instructions, messages, checkpoint data, and tool definitions still exceed that conservative limit after tool-output shortening, or if ChatGPT completes a compaction request without a reusable checkpoint, OpenChat falls back to a bounded local extractive summary. All original messages and tool results remain searchable in the local archive. Cancellation, authentication, rate-limit, and network errors do not use this fallback. OpenCode paid/API-key routes, Gemini, Groq, Cerebras, and OpenRouter summarize older messages using the selected model and provider route; long histories are sent to the summarizer in bounded UTF-8 batches. These extra summary requests use the provider's normal quota and billing. OpenCode free routes use the same bounded local extractive summary because the live free-tier endpoint rejected standalone compaction requests outside OpenCode; this local step makes no extra provider request, while ordinary free-tier requests that the provider rejects are reported as a provider restriction. Recent messages stay verbatim. Before each request with known context metadata, OpenChat estimates text and tool-schema size, attached images at 2,048 tokens each, and 1,024 tokens of fixed overhead and requires it to fit within 80% of the active request limit. If it does not fit after compaction, the provider request is rejected and the full local chat remains available. Because ChatGPT's Responses checkpoint is opaque, its size is estimated as 4,096 tokens; provider-side tokenization and the checkpoint's true size can differ from these local estimates. The next request combines compacted context with newer messages and, when useful, keyword-matched excerpts from older messages in the same conversation. FTS5 retrieves exact terms from archived messages and completed tool activities. Optional local semantic search adds meaning-based matches for archived messages and completed tool activities using a pinned multilingual E5 ONNX model that the user explicitly prepares in Settings > Conversation memory; its downloaded model files are SHA-256 verified, and embeddings stay on the device in a conversation-namespaced HNSW cache. Hybrid excerpts scale with the active request limit up to 4,096 words and are marked as untrusted historical data. Once compaction is active, the service reads only the boundary's immediate neighbors and newer message tail instead of loading the whole transcript on each request. This hybrid archive improves access to specific older details, but does not guarantee that every archived detail will be retrieved. OpenAI-compatible Chat Completions calls request usage where needed. Responses streams read it from completed events, while Cerebras and OpenRouter provide it in the final streamed message. The compaction trigger uses provider-reported input-token usage when available; otherwise, it estimates from UTF-8 byte length. The final request-budget check uses a separate conservative text estimate, counting ordinary ASCII prose at roughly one token per three characters and dense, whitespace-free, or punctuation-heavy strings by UTF-8 byte length. Both estimates can differ from a provider tokenizer. The ChatGPT API-key route reads model IDs from OpenAI's `/v1/models` endpoint, which does not provide per-model context limits, so that route currently skips automatic compaction and final request-budget checks. Models with no known context window or a window below 2,048 tokens do not receive automatic compaction or final request-budget checks. If compaction or archive lookup fails, OpenChat keeps the saved conversation and reports the failure instead of sending a shortened or incomplete history.

Appearance settings let people choose the conversation column width and app-wide text size, and set the typeface used throughout OpenChat. Code blocks keep a monospace typeface. These choices are saved locally.

People can delete individual conversations after confirmation, export a conversation with its exposed reasoning summaries and tool activity as Markdown, and retry the latest assistant response. A retry keeps the previous response until the replacement completes successfully and uses the conversation's saved provider and model route.

The Settings > Conversation memory page inspects the selected conversation's readable compacted summary, last request input-token count when available, and a bounded search over completed messages and tool results. Resetting compacted context removes only its saved summary and usage snapshot; the full message history and searchable archive remain intact. Keyword search is always available. When the user prepares the local semantic model, search also finds paraphrased details. Current builds fetch only the pinned public model files from Hugging Face; conversation data stays local. Model downloads show byte progress, can be cancelled, and resume from valid partial files when the host supports HTTP range requests; otherwise, the download restarts safely.

The Windows portable release is distributed as one `OpenChat.exe`. On first launch it unpacks the bundled release payload to a content-addressed directory under `%LOCALAPPDATA%\OpenChat\cache` and starts the app from there. The database and logs remain in their separate persistent directories. Build this release with `tools/build_windows_portable.ps1`.
