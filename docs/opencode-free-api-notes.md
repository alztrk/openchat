## Protocol and request shape

The current provider module's default System One route must not be confused with the live `opencode` entry in the model catalog. The latter advertised `@ai-sdk/openai-compatible` and `https://opencode.ai/inference/openai/v1`, so the probe selected chat completions for `deepseek-v4.1-flash-free`.

The probe's dry-run request was:

```http
POST https://opencode.ai/inference/openai/v1/chat/completions
Authorization: Bearer public
User-Agent: OpenChat-opencode-probe/1.0
Accept: text/event-stream
Content-Type: application/json
x-opencode-session-id: openchat-probe-<persisted-id>
x-session-affinity: openchat-probe-<persisted-id>
X-Session-Id: openchat-probe-<persisted-id>
x-opencode-session: openchat-probe-<persisted-id>
x-opencode-client: OpenChat
```

The request body used for the direct one-prompt probe was:

```json
{
  "model": "deepseek-v4.1-flash-free",
  "messages": [
    { "role": "user", "content": "Reply with exactly: probe OK" }
  ],
  "stream": true,
  "prompt_cache_key": "openchat-probe-<persisted-id>"
}
```

The OpenCode source also sends `x-opencode-project` using its project ID and optional parent-session headers when there is a parent. The independent probe has no OpenCode project or parent session, so those values are omitted unless `--project-id` is supplied. The script uses a stable probe-owned session ID, rather than inventing an OpenCode session ID. `TypeSafe-Danger-Zone-Images` is not sent on this OpenAI-compatible route; the source adds it to the separate System One provider.

## Backend impact for a separate implementation step

OpenChat currently pins the OpenAI-compatible model catalog and free-model gate in:

- `services/openchat-local-service/src/domain/providers/openai_compatible/models.rs`
- `services/openchat-local-service/src/domain/providers/openai_compatible/route.rs`
- `services/openchat-local-service/src/domain/providers/openai_compatible/conversation/response_stream.rs`
- `services/openchat-local-service/src/domain/providers/openai_compatible/context_compaction.rs`
- `services/openchat-local-service/src/domain/providers/openai_compatible/title_generation.rs`

The live catalog route and probe support indicate that the chat path is OpenAI-compatible; switching all such traffic to System One would be incorrect. The latest anonymous request with the full OpenCode header set returned `429 FreeUsageLimitError` rather than `403 FreeTierError`, so the policy gate no longer rejects the request shape; the remaining blocker is free-tier quota, which prevents observing streamed inference output.

## Backend free-route implementation

The local service now:

- accepts free OpenCode catalog models in `route.rs` and marks them as free instead of rejecting them;
- sends `x-opencode-session-id`, `x-session-affinity`, `X-Session-Id`, `x-opencode-session`, `x-opencode-client`, and `x-opencode-project` (when the conversation belongs to a project) on OpenCode requests;
- sends `prompt_cache_key` from the OpenCode session affinity;
- uses `Authorization: Bearer public` for free OpenCode requests and keeps the existing key flow for paid models;
- maps `429 FreeUsageLimitError` to the dedicated `opencode_free_usage_limit` error and records numeric `Retry-After` seconds in error details without automatic retries;
- allows free OpenCode models in title generation and keeps local extractive compaction for free OpenCode context summaries.

The Console OAuth/API-key probe paths are intentionally not part of this implementation and are tracked in `docs/roadmap.md` item 57.
