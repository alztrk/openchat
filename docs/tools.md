# Workspace tools

Windows AppContainer setup grants traversal on the path to the working tree and access only to validated workspace entries. ACL updates use a non-propagating DACL write; existing descendants are checked and updated individually so a temporary sandbox permission does not trigger recursive ACL rewriting across unrelated files.

On Windows, use a project's options to configure MCP servers stored in `.openchat/mcp.json`. The version 1 catalog has a `servers` array; each server has a lowercase `id`, an explicit `enabled` boolean, and a `transport` of `stdio` or `streamableHttp`. Local `stdio` servers require an absolute `program` path, optional string `arguments`, and up to 32 `environmentVariables` names. `streamableHttp` servers require an HTTPS endpoint on a public network address; loopback, private, link-local, reserved, and metadata addresses are rejected after DNS resolution, and DNS results are pinned to the connection. Redirects are disabled so credentials cannot be replayed to another host. An optional bearer credential is named by `authEnvironmentVariable`. Never put a secret in arguments, endpoint query parameters, or the project catalog. Use the server's key button to save each declared value in Windows Credential Manager. Values are scoped to the project, server, and variable name; the local service removes them from RPC parameters and does not return them to the UI. Stdio values are passed only through the sandboxed child process environment; the HTTP credential is sent only as a bearer token over HTTPS. Removing a saved value uses the same control. Saving validates the catalog and atomically replaces the file; symbolic-link catalogs and directories are rejected. If loading fails, saving stays disabled until the user retries, so a transient read error cannot replace the catalog with an empty list. Opening the configuration does not start a process. The explicit connection check starts only the selected enabled server or connects to its endpoint, lists its tools, and closes the connection when the check ends. During chat, enabled servers connect only for tool-capable provider routes, and their discovered tools are sent under `mcp__<server-id>__<tool-name>` names. MCP permission choices are saved in local application preferences per project. Up to 1,080 built-in, per-server, per-tool, and 32 named-task rules are accepted, enough for the configured server and tool limits plus every task in one catalog. Named task rules use `run_project_task__<task-id>` and override the general `run_project_task` rule. `Ask` is the default; a server-level `Allow` or `Deny` applies to every tool, while a tool-level rule overrides `Ask` or `Allow` for that tool. A server-level `Deny` takes precedence over tool rules and prevents that server from starting for chat. These choices are independent of the shared project catalog and global permission mode. MCP activity is persisted with the assistant response, results are marked untrusted, and startup, protocol, timeout, argument, and result sizes are bounded. Streamable HTTP JSON success and error bodies are read incrementally with a 64 KiB cap, and SSE events are size-checked before parsing. Version 1 first-party project tools are also supported through `.openchat/tools.json`; non-Windows process isolation remains unavailable.

On Windows, projects may declare up to 32 first-party tools in `.openchat/tools.json` with `version: 1` and a `tools` array. Each entry has a unique lowercase `id` (1–48 characters), user-facing `description`, project-relative regular `.exe` `executable`, `inputSchema`, `timeoutSeconds` (5–600), and `outputLimitBytes` (1–131072). The executable path cannot be absolute, traverse parent directories, or resolve through a symbolic link outside the project. Schemas are bounded JSON Schema subsets: objects must set `additionalProperties: false`; supported values are objects, arrays, strings, integers, numbers, and booleans with bounded required fields, item counts, enums, and numeric or string limits. Tools are advertised only for tool-capable routes with an attached project. Calls use the `project_tool__<id>` name, receive validated JSON on standard input, run directly inside the Windows AppContainer with a bounded timeout and combined output limit, and follow the same per-project Ask/Allow/Deny and persisted activity flow as other tools. Configure a tool only after reviewing the executable and its dependencies. Example catalog: `{"version":1,"tools":[{"id":"lint","description":"Run the repository linter.","executable":"tools/lint.exe","inputSchema":{"type":"object","properties":{"fix":{"type":"boolean"}},"required":["fix"],"additionalProperties":false},"timeoutSeconds":60,"outputLimitBytes":16384}]}`. The local Rust service exposes bounded `list_files`, `search_files`, `read_file`, and `get_file_info` tools, plus `write_file` and `edit_file` for explicitly requested file changes. It also exposes `web_search`, `read_url_content`, `execute_command`, and `send_terminal_input`; these definitions are sent with chat requests and the provider chooses when to call them. The global Settings option `Ask for approval` is the default and waits for a one-time user decision before each supported file, web, or terminal call. `Approve safe operations` skips approval only for read-only `list_files`, `search_files`, `read_file`, and `get_file_info` calls; file writes or edits, web calls, and terminal calls still wait for approval. Both approval modes restrict filesystem paths to the attached project folder or OpenChat local data directory at `%LOCALAPPDATA%\OpenChat`. The approval card shows the target and operation-specific inputs before the service proceeds. The model can use project-relative paths, `project:/...`, or the `openchat:/...` data alias; without a project, bare relative paths resolve under `%LOCALAPPDATA%\OpenChat`. The service resolves and revalidates the target after approval, including symlink resolution. `Full access` skips approval and allows file tools to operate anywhere, including the `desktop:/...` alias for the Desktop directory of the current user. The Desktop alias is rejected in both approval modes. `execute_command` starts or interacts with a terminal session, and `send_terminal_input` sends input, reads output, or terminates a session. On Windows each terminal session runs in a temporary AppContainer restricted to its working tree. Other platforms currently run terminal processes with the OpenChat process account and do not have an OS-level sandbox. Filesystem path rules do not replace terminal process isolation. Permission decisions resolve the pending tool request without cancelling the in-flight chat operation; denial is sent back to the model as a tool result so it can respond appropriately.

Project options can override the global permission mode for each built-in workspace, terminal, web, or Git tool with `Ask`, `Allow`, or `Deny`. Unset tools inherit the global mode. `Deny` returns a permission error without executing the tool; `Allow` removes the approval prompt for that tool but keeps the selected file scope and the Windows AppContainer boundary. Project rules are kept in local application preferences and sent with each request. The service validates every rule name and value before creating the tool executor.

Projects can declare named terminal tasks in `.openchat/tasks.json`, using a version 1 JSON object with a `tasks` array. Each task has a lowercase `id`, a `command`, and a `timeoutSeconds` value from 5 to 600. The file is limited to 64 KiB and 32 tasks, read with a 64 KiB plus one byte cap, and rejected if it is a symlink or resolves outside the project. On Windows, the `run_project_task` tool is advertised only when an attached project has at least one valid task; its schema lists only the declared task IDs. A missing catalog leaves the tool unavailable; a malformed catalog returns an explicit error only when the Windows tool can be offered, so a disabled tool does not block normal chat. When the selected permission mode requires approval, the resolved command and timeout are shown in the normal terminal approval card. Execution uses the same terminal output cap (128 KiB), cancellation, and permission rules as `execute_command`, and runs in the Windows AppContainer. The tool is not advertised on other platforms until they have OS-level process isolation. This is the current first-party configured executor; adding distinct user-configurable executor types requires a shared registry contract.

The project options menu can create an isolated Git worktree. It starts from the current commit and does not copy uncommitted changes from the source checkout. OpenChat shows its branch, changed-file count, and staged/unstaged diff; using it as a project creates a separate project entry and conversation. Project-specific permission rules are not copied to that new project, so it uses the current global tool policy until configured. Removing a worktree deletes its uncommitted and untracked files after confirmation; the Git branch and its commits remain. The worktree review dialog reads the task catalog from that worktree, shows the chosen command and timeout for confirmation, and displays cancellable execution status, exit code, and bounded output. A changed task command is rejected if it differs from the preview, and project-level `Deny` rules are enforced by the service.

The sidebar run manager lists saved runs that are running, paused, or interrupted across conversations. Opening an entry returns to its conversation, where pending questions and goal controls remain available. A run that ends while another conversation is selected triggers an informational notification. The service does not automatically retry interrupted provider requests. ChatGPT OAuth and OpenAI API-key conversations use their Responses routes for child analysis. Gemini, Groq, Cerebras, OpenRouter, and Mistral API-key conversations use their Chat Completions route when the selected model supports tool calls. Local llama.cpp, vLLM, and ExLlama conversations use the selected model's loopback Chat Completions endpoint when tool calls are supported; the endpoint's local API key is used only when configured. Child analysis inherits the selected model and reasoning setting; OAuth also carries the selected speed setting and workspace. Child runs use a read-only built-in tool allowlist and, on Windows, can invoke user-declared named project tasks through the same project permission rules and AppContainer process sandbox as the parent. They allow at most two concurrent children, three provider rounds, six tool calls, 2,048 output tokens per request, and 90 seconds. Arbitrary shell commands, direct file writes, MCP tools, and provider-hosted tools are not included in child runs. Cancellation propagates from the parent; child run IDs and usage are saved separately. The run manager shows each child's objective and final status/result, while live child tool progress is not streamed into the dialog.

Completed assistant responses include a file-change summary when a tool changed files. While a response is streaming, the composer shows an aggregate change button; opening it displays the conversation's file list and text diffs in a side panel. The panel can revert a file to its first version before OpenChat's changes, but only while the file still matches the latest version recorded by the assistant. If the file has since changed, OpenChat reports a conflict and leaves it untouched. Reverting an added file removes it; reverting a deleted file restores its saved bytes. Binary files and files without a bounded snapshot remain listed, but their text diff or revert action is unavailable.

File-change metadata is stored in SQLite. Original file bytes are stored as SHA-256-addressed files under `%LOCALAPPDATA%\OpenChat\attachments\snapshots`, so identical baselines are stored once and SQLite/WAL do not grow with source contents. Conversation deletion removes its metadata through a foreign-key cascade; unreferenced blobs are reclaimed from a durable cleanup queue the next time file changes are accessed. Interrupted blob writes older than five minutes are treated as abandoned and reclaimed. Existing manifests under `%LOCALAPPDATA%\OpenChat\file-changes` are imported once when a conversation's changes are first accessed, then removed after the import is committed. Invalid legacy data is preserved and reported as a storage error instead of being discarded. Direct writes and edits capture their target file. Terminal calls compare bounded snapshots of the active project root before and after each call. Snapshotting skips symlinks and the default ignored build/vendor directories, and is limited to 20,000 files, 512 MiB of total file sizes, and 128 MiB of retained file contents per snapshot; files larger than 16 MiB are not backed up and cannot be reverted from this panel. If a file grows after its size is checked, its hash is still recorded but its content is not retained. Text diffs are capped at 1 MiB of source data, 4,000 lines, and 256 KiB of output. If a snapshot exceeds a limit or cannot be read, the assistant response still completes and the change card explains that tracking may be incomplete. Terminal writes outside the active project root and writes that occur after a terminal tool call has returned are not captured.

Tool support is tracked per model with a nullable `supportsTools` value. OpenCode reads Models.dev's `tool_call` field; Mistral reads `capabilities.function_calling`; Cerebras and OpenRouter mark only models their catalogs already filter as tool-capable. Gemini and Groq use explicit model IDs verified against their tool-calling documentation because their model-list APIs do not provide an equivalent per-model field. Unknown models remain unknown. A confirmed unsupported model receives no tools; an unknown model keeps ordinary local tools but does not receive `ask_user`. ChatGPT OAuth uses the Codex Responses route's function tools. The context-usage estimate follows the selected model's same capability state.

Before dispatch, the service also checks that every returned tool call was present in that request's function-tool allowlist. A provider response naming an unadvertised tool is rejected before any tool action runs.

Both adapters translate provider tool definitions, calls, and results through OpenChat's shared Rust schema. ChatGPT Responses and OpenCode Chat Completions JSON stay inside their respective adapters; Flutter receives the same chat stream events from either provider. Adding another provider still requires an adapter for that provider's native protocol.

Tool calls are processed locally and their results are returned to the same provider before its final response. A single response is limited to six tool-call rounds, sixteen calls, and 16 KiB of serialized arguments per call. Unsupported, invalid, or out-of-scope requests return an explicit tool error. In `Ask for approval` and for approval-required calls in `Approve safe operations`, a denial returns a permission error to the model without running the requested operation; approval applies only to that call. Stopping a response also clears its pending approval. Treat text read from the active tool root as untrusted content.

For Cerebras, Mistral, and OpenRouter, earlier tool results larger than 4 KiB are shortened in later provider requests, including compaction batches. The request includes a `_openchat_truncated` marker, the original serialized byte count, and an excerpt from both ends. The complete tool result remains in local conversation history and exports.

Provider usage diagnostics record the provider, model, operation (`chat`, `tool_follow_up`, or `compaction`), estimated prompt-token count, image-input count, and token or cache counters returned by Cerebras, Mistral, and OpenRouter. A successful request that returns no usage counters records `usage_unavailable`. These local diagnostics do not include prompt text, response text, image data, credentials, or conversation IDs.

When a provider's model catalog reports a maximum output-token limit, OpenChat sends that limit using the provider's supported request field. It does not add an estimated limit when the catalog omits one. Archived retrieval is bounded by the estimated request capacity left after current instructions, tools, and retained messages. After history compaction, earlier images are omitted from the provider request; earlier text and tool activity remain available through the summary and archived retrieval. Newer messages, including their images, remain in the request.

Conversation-memory indexing applies best-effort redaction to common credential field names and visible provider token formats before adding tool arguments or results to keyword and semantic indexes. A schema migration rebuilds the existing derived tool index and invalidates its semantic vectors. This does not modify saved tool activity or messages, and detection can miss custom, encoded, or transformed secrets. Recent conversation context and encrypted conversation archives can still contain the original values.

When a call requires approval in either approval mode, it emits `chat.tool.permission.requested` with its approval ID, tool name, canonical target path, and arguments. Flutter returns the one-time decision with `chat.tool.permission.respond`; a bounded in-memory broker connects that decision to the waiting request. Each call also emits shared `chat.tool.updated` activity for approval waiting, execution, and its result or denial. The desktop UI shows the tool name, target path, JSON arguments, and JSON output or error under the assistant message. Tool activity is saved with local chat history, so it remains visible after reopening a conversation and is included in Markdown conversation exports.

## Persistent goals

Tool-capable routes also receive the hidden `start_goal`, `goal_update`, and `stop_goal` controls. The model is instructed to use `start_goal` for substantial work that needs multiple turns, and to leave short questions and one-response tasks as ordinary chats. Starting a goal validates its objective, atomically attaches it to the current agent-run checkpoint, and emits `chat.goal.updated` so the composer status bar appears without UI-side goal activation. Only one active, paused, or interrupted goal is allowed per conversation. `goal_update` stores progress, completion, or a blocker; an active goal continues across model turns until it reaches a terminal state. `stop_goal` cancels the current goal, or another recoverable goal in that conversation, stores the model's stop reason, cancels unanswered question groups, and emits the same goal event. The composer pause, resume, and stop controls remain available. Routes without tool-call support do not receive these controls, and `/goal` reports that requirement before starting.

## AI questions

The `ask_user` tool lets a model pause its active response with one or more structured choice or free-form questions. The native service validates question IDs, options, required answers, and text limits, then stores the question group and run checkpoint in SQLite before emitting `chat.question.requested`. Each answer submission is revision-checked and idempotent. When the original execution is still active, the answer wakes that execution; after a service restart, the same saved run can be resumed from its checkpoint.

Pending questions and answered continuation points can be reloaded with `chat.questions.list`. Windows builds also issue a native notification with only the bounded conversation and question IDs; selecting it opens the conversation. If notification delivery is unavailable, the pending card remains available in the conversation. A stopped run cancels unanswered questions. A shutdown interruption preserves a pending question for recovery. Tool status checkpoints are saved before their UI events so reopening history does not depend on receiving every live event.

When a completed assistant response arrives while OpenChat is in the background, Windows shows a notification with the conversation title, a short response excerpt, and the provider icon. Selecting the notification opens the conversation. Its reply field and Send action open the same conversation and submit through its saved provider and model route. Empty, oversized, and stale replies are not sent. Failed or stopped responses do not trigger this notification.

Request manifests show which message IDs and archived message IDs were included, the compaction boundary, bounded attachment identity/name/type metadata, instruction categories, and tool definitions. They do not retain prompt or response text, attachment bytes, or credentials. Usage request details and CSV exports include the durable run ID when available, including child-run attribution. Source lists are bounded and disclose when truncation occurred. Local web-search and page-read citations link to locally retrieved source records. For Mistral API-key conversations, an approved `web_search` tool call uses Mistral's hosted web search through its Conversations API. OpenChat sends the search query and selected model, then stores the returned `tool_reference` URLs as provider-native source records; it does not send the conversation history in this search request. For Gemini API-key conversations, an approved `web_search` tool call uses Google Search grounding through Gemini `generateContent`, with only the query and selected model. OpenChat stores returned grounding URLs and support text and renders Google's returned Search entry-point attribution after filtering active content and external resource loads. The full Gemini conversation continues through the configured OpenAI-compatible Chat Completions route. Provider URL annotations are stored with the assistant response and open a source card containing the provider-supplied title and URL. When the provider supplies a valid text end offset, the inline source link follows that text; absent or out-of-range offsets place it at the end of the response. The provider does not supply retrieval time in these annotations, so OpenChat does not show one.

## Search and listing behavior

- Search and listing respect repository `.gitignore` files at the workspace and nested-directory levels. Global Git excludes and `.git/info/exclude` are not applied.
- Search skips dot-hidden paths and common generated or dependency directories by default: `.git`, `.dart_tool`, `.gradle`, `.next`, `.nuxt`, `build`, `coverage`, `DerivedData`, `dist`, `node_modules`, `Pods`, `target`, and `vendor`. Selecting one of those directories directly as the search path includes it and its contents. `includeHidden` includes hidden paths; explicitly selecting a hidden path also includes its contents.
- Searches return at most 40 matches per call. Each call walks the current filesystem directly; it does not build or depend on a persistent or in-memory workspace index. It scans at most 100,000 files, 100,000 directories, or 128 MiB of file contents per query. A `truncated` result means the scan did not finish.
- To keep common searches responsive, the first `limit + 1` files are searched serially so a full result page can return early. If that does not fill the page, the remaining files are scanned on at most eight workers. Directory entries are traversed by name, so result order and offsets stay stable across pages. The worker set and candidate list are bounded by the file and byte limits.
- `list_files` walks the current directory on each call. It retains only the first `offset + limit` eligible names in a max-heap, then sorts that retained page, instead of sorting the entire directory. It scans at most 100,000 entries.
- `read_file` skips bytes before the requested starting line without allocating a string for every skipped line. It returns at most 500 lines and 64 KiB, and refuses files larger than 64 MiB. `get_file_info` and `read_file` share the metadata read used to validate the file.
- Search and listing output remain compact and bounded. In both approval modes, returned paths use `project:/...` or `openchat:/...`; in `Full access`, they are absolute. The `desktop:/...` input alias resolves only inside the current user's Desktop directory. Symbolic links in directory listings are skipped, and invalid or inaccessible entries set `truncated` or return an explicit error.

`list_files` returns at most 100 entries. `read_file` reports the continuation line when its line or byte cap stops the response.
