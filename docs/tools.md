# Workspace tools

The local Rust service exposes bounded `list_files`, `search_files`, `read_file`, and `get_file_info` tools, plus `write_file` and `edit_file` for explicitly requested file changes. It also exposes `web_search`, `read_url_content`, `execute_command`, and `send_terminal_input`; these definitions are sent with chat requests and the provider chooses when to call them. The global Settings option `Ask for approval` is the default and waits for a one-time user decision before each supported file, web, or terminal call. `Approve safe operations` skips approval only for read-only `list_files`, `search_files`, `read_file`, and `get_file_info` calls; file writes or edits, web calls, and terminal calls still wait for approval. Both approval modes restrict filesystem paths to the attached project folder or OpenChat local data directory at `%LOCALAPPDATA%\OpenChat`. The approval card shows the target and operation-specific inputs before the service proceeds. The model can use project-relative paths, `project:/...`, or the `openchat:/...` data alias; without a project, bare relative paths resolve under `%LOCALAPPDATA%\OpenChat`. The service resolves and revalidates the target after approval, including symlink resolution. `Full access` skips approval and allows file tools to operate anywhere, including the `desktop:/...` alias for the Desktop directory of the current user. The Desktop alias is rejected in both approval modes. `execute_command` starts or interacts with a terminal session, and `send_terminal_input` sends input, reads output, or terminates a session. Commands run with the Windows account permissions used by OpenChat from the attached project folder, or from `%LOCALAPPDATA%\OpenChat` when no project is attached. Filesystem path restrictions do not sandbox terminal processes. Permission decisions resolve the pending tool request without cancelling the in-flight chat operation; denial is sent back to the model as a tool result so it can respond appropriately.

Completed assistant responses include a file-change summary when a tool changed files. While a response is streaming, the composer shows an aggregate change button; opening it displays the conversation's file list and text diffs in a side panel. The panel can revert a file to its first version before OpenChat's changes, but only while the file still matches the latest version recorded by the assistant. If the file has since changed, OpenChat reports a conflict and leaves it untouched. Reverting an added file removes it; reverting a deleted file restores its saved bytes. Binary files and files without a bounded snapshot remain listed, but their text diff or revert action is unavailable.

File-change metadata is stored in SQLite. Original file bytes are stored as SHA-256-addressed files under `%LOCALAPPDATA%\OpenChat\attachments\snapshots`, so identical baselines are stored once and SQLite/WAL do not grow with source contents. Conversation deletion removes its metadata through a foreign-key cascade; unreferenced blobs are reclaimed from a durable cleanup queue the next time file changes are accessed. Interrupted blob writes older than five minutes are treated as abandoned and reclaimed. Existing manifests under `%LOCALAPPDATA%\OpenChat\file-changes` are imported once when a conversation's changes are first accessed, then removed after the import is committed. Invalid legacy data is preserved and reported as a storage error instead of being discarded. Direct writes and edits capture their target file. Terminal calls compare bounded snapshots of the active project root before and after each call. Snapshotting skips symlinks and the default ignored build/vendor directories, and is limited to 20,000 files, 512 MiB of total file sizes, and 128 MiB of retained file contents per snapshot; files larger than 16 MiB are not backed up and cannot be reverted from this panel. If a file grows after its size is checked, its hash is still recorded but its content is not retained. Text diffs are capped at 1 MiB of source data, 4,000 lines, and 256 KiB of output. If a snapshot exceeds a limit or cannot be read, the assistant response still completes and the change card explains that tracking may be incomplete. Terminal writes outside the active project root and writes that occur after a terminal tool call has returned are not captured.

Tool support is tracked per model with a nullable `supportsTools` value. OpenCode reads Models.dev's `tool_call` field; Mistral reads `capabilities.function_calling`; Cerebras and OpenRouter mark only models their catalogs already filter as tool-capable. Gemini and Groq use explicit model IDs verified against their tool-calling documentation because their model-list APIs do not provide an equivalent per-model field. Unknown models remain unknown. A confirmed unsupported model receives no tools; an unknown model keeps ordinary local tools but does not receive `ask_user`. ChatGPT OAuth uses the Codex Responses route's function tools. The context-usage estimate follows the selected model's same capability state.

Before dispatch, the service also checks that every returned tool call was present in that request's function-tool allowlist. A provider response naming an unadvertised tool is rejected before any tool action runs.

Both adapters translate provider tool definitions, calls, and results through OpenChat's shared Rust schema. ChatGPT Responses and OpenCode Chat Completions JSON stay inside their respective adapters; Flutter receives the same chat stream events from either provider. Adding another provider still requires an adapter for that provider's native protocol.

Tool calls are processed locally and their results are returned to the same provider before its final response. A single response is limited to six tool-call rounds, sixteen calls, and 16 KiB of serialized arguments per call. Unsupported, invalid, or out-of-scope requests return an explicit tool error. In `Ask for approval` and for approval-required calls in `Approve safe operations`, a denial returns a permission error to the model without running the requested operation; approval applies only to that call. Stopping a response also clears its pending approval. Treat text read from the active tool root as untrusted content.

For Cerebras, Mistral, and OpenRouter, earlier tool results larger than 4 KiB are shortened in later provider requests, including compaction batches. The request includes a `_openchat_truncated` marker, the original serialized byte count, and an excerpt from both ends. The complete tool result remains in local conversation history and exports.

Provider usage diagnostics record the provider, model, operation (`chat`, `tool_follow_up`, or `compaction`), estimated prompt-token count, image-input count, and token or cache counters returned by Cerebras, Mistral, and OpenRouter. A successful request that returns no usage counters records `usage_unavailable`. These local diagnostics do not include prompt text, response text, image data, credentials, or conversation IDs.

When a provider's model catalog reports a maximum output-token limit, OpenChat sends that limit using the provider's supported request field. It does not add an estimated limit when the catalog omits one. Archived retrieval is bounded by the estimated request capacity left after current instructions, tools, and retained messages. After history compaction, earlier images are omitted from the provider request; earlier text and tool activity remain available through the summary and archived retrieval. Newer messages, including their images, remain in the request.

Conversation-memory indexing applies best-effort redaction to common credential field names and visible provider token formats before adding tool arguments or results to keyword and semantic indexes. A schema migration rebuilds the existing derived tool index and invalidates its semantic vectors. This does not modify saved tool activity or messages, and detection can miss custom, encoded, or transformed secrets. Recent conversation context and encrypted conversation archives can still contain the original values.

When a call requires approval in either approval mode, it emits `chat.tool.permission.requested` with its approval ID, tool name, canonical target path, and arguments. Flutter returns the one-time decision with `chat.tool.permission.respond`; a bounded in-memory broker connects that decision to the waiting request. Each call also emits shared `chat.tool.updated` activity for approval waiting, execution, and its result or denial. The desktop UI shows the tool name, target path, JSON arguments, and JSON output or error under the assistant message. Tool activity is saved with local chat history, so it remains visible after reopening a conversation and is included in Markdown conversation exports.

## AI questions

The `ask_user` tool lets a model pause its active response with one or more structured choice or free-form questions. The native service validates question IDs, options, required answers, and text limits, then stores the question group and run checkpoint in SQLite before emitting `chat.question.requested`. Each answer submission is revision-checked and idempotent. When the original execution is still active, the answer wakes that execution; after a service restart, the same saved run can be resumed from its checkpoint.

Pending questions and answered continuation points can be reloaded with `chat.questions.list`. Windows builds also issue a native notification with only the bounded conversation and question IDs; selecting it opens the conversation. If notification delivery is unavailable, the pending card remains available in the conversation. A stopped run cancels unanswered questions. A shutdown interruption preserves a pending question for recovery. Tool status checkpoints are saved before their UI events so reopening history does not depend on receiving every live event.

When a completed assistant response arrives while OpenChat is in the background, Windows shows a notification with the conversation title, a short response excerpt, and the provider icon. Selecting the notification opens the conversation. Its reply field and Send action open the same conversation and submit through its saved provider and model route. Empty, oversized, and stale replies are not sent. Failed or stopped responses do not trigger this notification.

## Search and listing behavior

- Search and listing respect repository `.gitignore` files at the workspace and nested-directory levels. Global Git excludes and `.git/info/exclude` are not applied.
- Search skips dot-hidden paths and common generated or dependency directories by default: `.git`, `.dart_tool`, `.gradle`, `.next`, `.nuxt`, `build`, `coverage`, `DerivedData`, `dist`, `node_modules`, `Pods`, `target`, and `vendor`. Selecting one of those directories directly as the search path includes it and its contents. `includeHidden` includes hidden paths; explicitly selecting a hidden path also includes its contents.
- Searches return at most 40 matches per call. Each call walks the current filesystem directly; it does not build or depend on a persistent or in-memory workspace index. It scans at most 100,000 files, 100,000 directories, or 128 MiB of file contents per query. A `truncated` result means the scan did not finish.
- To keep common searches responsive, the first `limit + 1` files are searched serially so a full result page can return early. If that does not fill the page, the remaining files are scanned on at most eight workers. Directory entries are traversed by name, so result order and offsets stay stable across pages. The worker set and candidate list are bounded by the file and byte limits.
- `list_files` walks the current directory on each call. It retains only the first `offset + limit` eligible names in a max-heap, then sorts that retained page, instead of sorting the entire directory. It scans at most 100,000 entries.
- `read_file` skips bytes before the requested starting line without allocating a string for every skipped line. It returns at most 500 lines and 64 KiB, and refuses files larger than 64 MiB. `get_file_info` and `read_file` share the metadata read used to validate the file.
- Search and listing output remain compact and bounded. In both approval modes, returned paths use `project:/...` or `openchat:/...`; in `Full access`, they are absolute. The `desktop:/...` input alias resolves only inside the current user's Desktop directory. Symbolic links in directory listings are skipped, and invalid or inaccessible entries set `truncated` or return an explicit error.

`list_files` returns at most 100 entries. `read_file` reports the continuation line when its line or byte cap stops the response.
