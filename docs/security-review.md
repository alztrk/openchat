## Findings and actions

### Partial: Windows connector package Authenticode validation

Windows package installation checks the staged executable with `WinVerifyTrustEx` before publishing it, and launch verification applies the same trust check after size, PE, and SHA-256 validation. A nonzero trust result rejects installation or launch; non-Windows service builds reject Windows executable packages because they cannot perform this operating-system check. Verification uses cached trust data, requests no revocation check, and does not compare the certificate signer with the catalog's publisher label or the pinned catalog key. Previously installed unsigned packages no longer launch, but can still be removed; when their metadata is missing, removal checks their bytes against the stored reference without requiring Authenticode trust. Windows Authenticode validation tests accept the locally trusted `System32\kernel32.dll` and reject unsigned executables and packages. Real-world publisher identity, fresh revocation policy, and release signing remain open.

Launch verification is path-based and completes before the MCP process is created from that path. A process running as the same Windows user that can write the package directory could replace the executable between verification and process creation. The desktop threat model trusts processes under the same user account, so Authenticode does not provide isolation from that process; this same-user check-to-launch race remains outside the package-integrity guarantee.

### Documented: credential disclosure boundary (A-018)

On Windows, provider API keys, MCP secrets, and OAuth token pairs are individually DPAPI-protected in the local SQLCipher database. Windows Credential Manager stores the SQLCipher profile key and may contain legacy OAuth or MCP entries that are migrated into the database vault when read. API keys entered in provider settings exist in the React renderer and pass through Tauri IPC to the native host for validation and storage; the earlier README claim that credentials are never exposed to UI renderers was inaccurate. Credential-status commands return configuration state and redacted suffixes instead of saved full API keys. This review has not established that every diagnostic log sink excludes every credential, so the README no longer makes that universal claim. The credential flow and the limits of the log-redaction claim are now disclosed in the README.

### Documented: retained rollback content after deletion (A-025)

The README explains that conversation deletion and history clearing affect the active database, that verified migration backups have no automatic expiry or in-app restore flow, and that historical filesystem snapshots may retain plaintext blocks from before encryption. This makes the retained-copy behavior explicit; it does not securely erase old blocks or add backup expiry.

No verified security-reporting contact or repository disclosure channel is documented in this checkout; A-019 remains open until a real reporting route is selected and verified.

### Resolved: project MCP permission grants are bound to server and tool definitions

Project MCP `Allow` rules now use a separate `mcpv1__` namespace and a truncated SHA-256 fingerprint. The server fingerprint covers the validated server configuration, while each tool fingerprint also covers its server identity, tool name, description, and input schema. A changed server configuration or tool definition therefore produces a different permission key and returns to the normal approval path. The project settings flow receives the current server and tool keys from the service; choosing server-wide `Allow` grants only the checked server configuration and its current tools. Editing a server clears its scoped rules.

Legacy unbound MCP `Allow` rules are filtered from effective policy and rejected on persistence. Legacy `Deny` rules remain effective, so the migration does not silently widen an existing denial. Focused tests cover fingerprint changes, rule parsing, bound saves, ignored legacy allows, and preserved denials; the frontend production build and locale consistency check passed. A live MCP server session was not run.

### Hardened: DPAPI secret-map updates now coordinate across Windows sessions

Provider and global MCP settings use read-modify-write updates to the DPAPI-protected secret map in the SQLCipher database. The former `Local\` mutex was visible only inside one Windows session, so concurrent writes from another login session could start from stale contents and discard an update. The store now opens a sibling `.lock` file in the protected profile directory and holds an exclusive OS file lock while updating the secret map. Rust's `File::try_lock` uses `LockFileEx` on Windows; the OS releases the lock when the handle closes ([Rust `File`](https://doc.rust-lang.org/std/fs/struct.File.html), [Microsoft byte-range locks](https://learn.microsoft.com/en-us/windows/win32/fileio/locking-and-unlocking-byte-ranges-in-files)). This avoids a predictable global kernel-object name while preserving per-profile coordination. The empty lock file remains in place so all sessions always lock the same file object. The crate declares Rust 1.89 as its minimum version, matching the stabilization version of `File::try_lock`.

The secret-map write API requires a live `SecretMapUpdateLock`, so future callers cannot accidentally persist a read-modify-write update without participating in the same coordination. The storage path now rejects missing or non-absolute `APPDATA` values before reading or writing, preventing malformed process environment from redirecting the encrypted map and lock file into the current working directory. Regression tests verify absolute and relative path handling, profile-specific lock paths, exclusive locking through a second file handle, and that concurrent locked updates preserve all entries. The current test run used one Windows login session, so cross-session scheduling was not directly exercised; Windows documents file-range locks as process-independent and tied to the file handle.

### Resolved: hard-linked files crossed project boundaries

Project file tools and project metadata readers previously treated an in-project path as sufficient proof that the file belonged only to that project. A hard link can expose or modify the same file through another path outside the project, while remaining a regular file and passing symlink checks.

File reads now check the link count on the opened handle. The check is shared by file tools, search, project indexing, instructions, Skills, and task/tool/MCP catalogs. A linked file is rejected; an index sync that encounters one stays stale. Project instruction saves now create and atomically replace the file through an opened `.openchat` directory capability. The search latency measurements and limits are recorded in [architecture.md](architecture.md).

Regression coverage includes read, search, write, edit, indexing, instruction, and project catalog paths.

### Resolved: file growth could exceed tool read and edit limits

File tools checked the file size before processing, but an already-open file can grow afterward. `read_file` now caps total bytes scanned at 64 MiB plus one byte and separately caps the returned line range at 64 KiB plus one byte, after skipping to the requested line. `edit_file` reads at most 10 MiB plus one byte and rejects an over-limit result before rewinding or writing. Tests cover a long single line, reading a line beyond the output-byte limit, and preserving an oversized file.

### Resolved: terminal sessions had no service-wide concurrency limit

Each terminal process already had a timeout and a 128 KiB output-buffer limit, but the service retained interactive sessions without a total count bound. Repeated commands across conversations could therefore accumulate processes and buffers beyond the in-flight RPC limit. The terminal manager now reserves one of 16 process-session slots before starting a command. When full, it rejects the new command before spawning; failed starts release their reservation, and a slot remains held until the session and its active references are dropped. The session record no longer copies the original command text or working-directory path, which were unused after process creation and could retain sensitive command arguments. Existing per-session sandbox, timeout, output, approval, and ownership behavior is unchanged.

Regression coverage verifies rejection at capacity, no extra session entry, recovery after a failed spawn, and capacity release after stopping a session.

### Hardened: sandbox termination errors verify the full process tree

**Severity:** Low process-lifecycle correctness risk in the Windows sandbox.

If `TerminateJobObject` failed, `SandboxedProcess::start_kill` previously treated an exited primary process as proof that its entire job had stopped. A child could still be associated with the job, so that state was insufficient evidence. The method now queries `JOBOBJECT_BASIC_ACCOUNTING_INFORMATION.ActiveProcesses` and reports success only when the job has no active processes; a failed query remains an error. Microsoft documents `ActiveProcesses` as the number of processes currently associated with the job ([job accounting structure](https://learn.microsoft.com/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information)).

A Windows regression test launches a child that outlives its primary process, duplicates the job handle with query-only access to force `TerminateJobObject` to fail, verifies the kill request does not report success, then terminates and waits for the process tree with the full handle. All 20 Windows sandbox tests passed after the change, including the new regression; Clippy with undocumented-unsafe-block checks, Cargo formatting, and rustdoc passed.

### Hardened: completed project tools could outlive their timeout through descendants

The configured project-tool runner applied its timeout while waiting for the primary executable, then awaited stdout and stderr readers after that process exited. A child could inherit either pipe and keep those reads pending indefinitely; the timeout and cancellation branches were no longer polled, and the sandbox job remained alive while the runner was stuck. When the primary executable now exits, the service terminates any remaining job processes and waits for the job to empty before collecting the bounded output. A Windows regression launches a descendant that marks its start and remains active; before the fix the runner exceeded a five-second outer deadline, and after the fix it returns promptly with a completed status. One-shot project tools therefore cannot leave background descendants running.

### Hardened: profile restore metadata reads are bounded

**Severity:** Low local availability risk from damaged or unexpectedly large restore state.

Startup recovery used an unbounded `fs::read` for restore markers, journals, and the staged manifest. The archive parser already bounded a newly imported manifest, but recovery reopened the staged copy through the unbounded helper. Restore markers and journals are now capped at 4 KiB, and staged manifests retain their existing 128 MiB limit. The reader checks the file size before allocation and also limits bytes read, so growth after the metadata check cannot exceed the configured limit by more than one byte.

The profile-archive regression test accepts valid JSON at its exact byte limit and rejects the same value with an additional byte. The focused archive test filter passed all five matching tests; full service-suite and static checks are recorded below.

### Hardened: local engine downloads restrict redirects to GitHub

**Severity:** Low conditional local-network request risk.

The installer accepts only release assets pinned to a GitHub repository, release tag, and filename in the embedded catalog, and verifies the declared byte length and SHA-256 digest before extraction. Its HTTP client previously used Reqwest's default redirect policy, which could follow a release URL to any scheme or host. The installer now follows at most ten redirects and accepts only HTTPS on the default port, without URL credentials, to `github.com` or GitHub's `release-assets.githubusercontent.com` CDN. Requests do not carry provider credentials, and the existing size and digest checks are unchanged. GitHub documents redirects for release asset downloads and identifies the release asset host in its [release asset API](https://docs.github.com/en/rest/releases/assets) and [self-hosted runner network requirements](https://docs.github.com/en/enterprise-cloud%40latest/actions/reference/runners/self-hosted-runners).

Tests cover the allowed hosts, rejected scheme/authority changes, and a loopback redirect that must be returned without following it. This restricts redirect destinations; DNS resolution of the trusted GitHub hosts still follows the operating system's network configuration.

### Hardened: compromised renderer could multiply sidecar processes

**Severity:** Moderate local resource-exhaustion risk at the renderer-to-service boundary.

The shell capability was restricted to the packaged service binary, and source inspection of the pinned Tauri shell plugin 2.5.0 confirmed that an omitted argument list resolves to an empty allowlist. However, a renderer with access to `shell:allow-spawn` could start multiple independent service processes. Each process has its own RPC operation and memory budgets, so repeated launches could multiply work beyond the intended per-application limits. This required control of renderer JavaScript; the finding did not allow launching an arbitrary executable or passing service arguments.

Sidecar ownership now lives in the Tauri host. The host starts at most one process, exposes only an idempotent start command and a generation-bound write command, forwards newline-delimited output through one Tauri event, and stops the process when the app exits. The renderer has no shell spawn or stdin-write capability, so renderer-controlled arguments, working directory, and environment are no longer part of process creation. The native bridge rejects frames that exceed 24 MiB or contain multiple raw lines; service-side RPC validation and operation limits remain in place. The implementation is in [local_service.rs](../apps/desktop/tauri/src/local_service.rs).

Regression coverage verifies the native frame boundary. The Tauri suite and frontend build, type, and lint checks are recorded below; a packaged desktop smoke test remains outstanding.

### In progress: SQLCipher protects application-managed local databases

The shared database contains conversation messages, tool results, project metadata, and local history. The Windows service now builds with bundled SQLCipher. The full-token local service stores a random 32-byte key in the current user's Windows Credential Manager and sends it to the AppContainer broker only through inherited standard handles during broker startup. The broker applies the key before querying the database. A missing key for an existing encrypted database fails closed; the bootstrap permits key creation only when the database is absent, empty, or recognized as plaintext SQLite. The Tauri production build no longer includes a direct SQLite opener or a `rusqlite` dependency; `chat_storage.rs` is limited to bounded exports, diagnostics, and schema-version reporting.

The storage adapter verifies the SQLCipher runtime and keyed open. Recognized plaintext databases are validated, exported to a keyed temporary database, verified, and replaced through a journaled migration that retains the source until the encrypted database passes integrity checks. If the process stops during that window, the plaintext migration source remains until the journal is recovered on a later startup; filesystem snapshots and unallocated blocks may also retain old plaintext, and file replacement does not promise secure erasure. Active database snapshots, migration backups, import rollback files, retained host-side legacy databases, and interrupted restore stages use keyed databases. Full-profile archives use a separate archive key inside the existing age-encrypted manifest; restore converts the archive database to the destination profile key. The prior plaintext archive format remains readable through conversion. A saved Windows Credential Manager key with a missing active database now fails closed unless a valid first-run marker or recoverable plaintext-migration journal authorizes initialization. If neither active nor recoverable storage exists, startup rejects the broker request instead of silently opening an empty profile. Startup still does not choose an older backup automatically.

### Resolved: RPC parameter allocation amplification

**Severity:** Moderate local resource-exhaustion risk at the renderer-to-sidecar boundary.

The service capped each newline-delimited request at 24 MiB, but decoded `params` into a complete `serde_json::Value` tree before checking that it was an object. A compact array or map with many small values could therefore expand into substantially more heap allocation than its wire size. This requires malformed or compromised renderer code to send a request to the same-user sidecar; the RPC pipe is not exposed as a network listener.

The request decoder now counts parameter values while parsing, retains at most 100,000 per request, then drains excess JSON with `IgnoredAny` instead of building the remaining tree. Active requests share a 250,000-value budget, alongside the existing operation-count and raw-byte budgets. Method names are limited to 128 bytes. Wrong-shaped parameters continue to return `invalid_request_params` with their request ID, and over-complex requests return `request_too_complex` without desynchronizing later frames. Tests cover nested arrays and maps, oversized non-object parameters, large string payloads, active-budget release, and a real sidecar process continuing after a rejected frame.

Temporary-conversation attachment parsing previously cloned each complete attachment JSON value to deserialize its metadata, copying the Base64 payload before decoding it. The parser now borrows and bounds the metadata fields first, with a 128-byte MIME-type limit, then creates only the small owned metadata value; the Base64 field is not cloned. It also compares the encoded length with the declared byte count before decoding, rejecting inconsistent payloads without allocating their decoded buffer. The accepted image and text limits and provider payload format are unchanged. Focused tests verify metadata bounds, early size-mismatch rejection, and image payload compatibility. An ignored local debug benchmark with a 10 MiB PNG compared metadata extraction directly: the old clone-and-deserialize path took 2,004–2,191 µs per sample, while the bounded path took 4–9 µs. This isolates metadata parsing; it is not an end-to-end request latency claim.

### Hardened: parsed RPC credentials are cleared when requests are dropped

The raw RPC frame is zeroized after decoding, but a recognized credential field could remain in the parsed `serde_json::Value` when the method did not consume it or rejected the request before credential extraction. `Request` now clears string values recursively under the exact `apiKey`, `secret`, `passphrase`, `secrets`, and `credential` parameter keys when its service-owned request object is dropped. Its `Debug` output redacts the request ID and parameter payload. Existing handlers still move accepted secrets into zeroizing wrappers before use. Conversation creation also clears those values before serializing nested agent metadata, and message save/read paths clear credential fields from citation and tool-activity metadata, including JSON encoded inside argument and output strings. The focused persistence regression passed 1/1 and covers new and legacy rows plus double-encoded tool arguments. This remains key-name based filtering; unknown credential field names and copies outside these storage paths are not covered.

### Resolved: AppContainer ACL traversal queued paths before enforcing its entry bound

The sandbox capped each visited runtime or workspace tree at 20,000 paths, but checked the count only after removing paths from the traversal queue. A directory with very high fan-out could therefore allocate an oversized queue before the cap was reached. Both tree walkers now count the root and reject an additional path before enqueueing it once the existing limit is reached. Reparse-point handling, hard-link rejection, ACL grants, and the accepted 20,000-path boundary are unchanged. A boundary test verifies that a path beyond the cap is not retained.

### Hardened: file and inheritable-directory ACL writes use the inspected handle

File ACL updates and directory grants that add inheritable ACEs read the DACL from, then update, the same target handle with `SetSecurityInfo`. A file has no descendants to inherit its ACEs. Inheritable directory grants open the target with `MAXIMUM_ALLOWED`; Microsoft documents that this suppresses ACE propagation to existing children ([`SetSecurityInfo`](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo), [security descriptor operations](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-descriptor-operations)). Non-inheriting directory grant and revoke operations now use `NtSetSecurityObject` on the inspected handle. The path is not resolved again at write time, and the focused Windows regression confirms that the update stays on the inspected directory after its original path is replaced. The native API's child-propagation behavior for filesystem objects is not specified by Microsoft; current Windows/NTFS tests confirm byte-for-byte preservation of existing child DACLs, so compatibility across other filesystem or Windows versions remains to be checked. The `noninheriting_directory_acl_updates_are_nonrecursive` test checks the granted ACE's type, SID, mask, and flags; effective allow-rights before grant and after revoke; stable DACL control bits and ACL revision; removal of the target SID on revoke; and byte-for-byte preservation of the existing child's DACL. Other tests verify child and sibling DACLs remain unchanged for inheritable directory grants, file grants can be revoked, and an inheritable update succeeds while another read-attributes handle is open on the directory.

The DACL read-modify-write sequence is serialized within the process by a mutex and across processes that resolve the same profile path by a stable file lock at `%LOCALAPPDATA%\OpenChat\appcontainer-acl.lock`. The lock file is retained to keep a consistent lock target, and a failed open or 30-second acquisition timeout aborts the ACL update. A temporary-workspace test verifies that a second thread cannot acquire the lock until the first releases it, and a path test verifies profile scoping. The test host did not exercise multiple Windows login sessions directly, so cross-session contention remains unverified on this host.

### Informational hardening residual: concurrent hard-link creation during AppContainer ACL grant

The focused Windows regression confirms that, on the test host, a same-user process with delete-child access to the parent can rename and replace a target name while `lock_acl_path` retains its handles. The retained handle continues to identify the original object, and a late hard link aliases that same object. File and inheritable-directory ACL writes use `SetSecurityInfo`; non-inheriting directory writes use `NtSetSecurityObject`. Both update the inspected object without resolving a replacement path at write time. The AppContainer is not an isolation boundary against other processes owned by the same Windows account, and it cannot prevent a same-user alias from being created after ACL setup returns.

`grant_working_directory` also grants the AppContainer traversal access to ancestor directories. When a same-user process can add an alias in a writable traversable ancestor, that alias can remain reachable after ACL setup returns; a handle held only during the DACL update cannot provide a lifetime guarantee.

The sandbox rejects files that already have more than one hard link by checking the link count on the same handle used to inspect the DACL. A 2026-10-18 Windows experiment confirmed that the current read/write sharing mode still permits another same-user process to create a new hard link while that handle is open. A follow-up opened the file with share mode zero and confirmed that ordinary file reads were blocked, but both same-process hard-link creation and an external `fsutil hardlink create` still succeeded. This local behavior contradicts Microsoft's documented sharing guarantee ([`CreateHardLinkW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createhardlinkw)); the exclusive-handle change was therefore removed because it did not close the race and could block sandbox startup for files already open in an editor. File ACL writes update the inspected file object directly, so a same-user process can still add a hard link after the link-count check and expose that same object and DACL under another path. No privilege-boundary exploit has been demonstrated, and the AppContainer is not a security boundary against other processes running as the same user.

The independent source review on 2026-10-28 confirmed that the required actor is another process running as the same Windows user. The repository's documented desktop trust model explicitly does not isolate processes owned by that account, and this path has not demonstrated access across a user or privilege boundary. Track the race as an informational path-scoping hardening residual rather than a confirmed security vulnerability. Eliminating it while preserving direct access to mutable workspaces and runtime trees would require an architectural boundary such as brokered access or private copies with controlled synchronization; no narrow ACL change closes the lifetime race.

A follow-up attempt changed non-inheriting directory writes to `SetSecurityInfo` on the inspected handle, filtered inherited ACEs before the update, and passed the DACL's original protected/unprotected state. Its focused regression passed, but the full 23-test Windows sandbox suite then failed 11 tests with sharing violations (Windows error 32), including file hard-link and AppContainer process-start scenarios. The candidate was removed. A second candidate used `MAXIMUM_ALLOWED` for every directory update and wrote through the inspected handle; its focused regression passed, but the full suite failed 12/24 tests with Windows error 32 sharing violations. That candidate was also removed. These experiments predated the native `NtSetSecurityObject` follow-up below. Microsoft's documentation describes automatic propagation behavior ([ACE propagation](https://learn.microsoft.com/en-us/windows/win32/secauthz/automatic-propagation-of-inheritable-aces), [DACL protection flags](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-information)).

Follow-up, 2026-10-28: at Alican's direction, non-inheriting directory grant and revoke operations now use `NtSetSecurityObject` with the already inspected target handle and the existing `READ_CONTROL | WRITE_DAC | FILE_READ_ATTRIBUTES` access. The Windows binding comes from `windows-sys`'s `Wdk_Storage_FileSystem` feature. The absolute descriptor passed to the native call carries the source DACL's defaulted, auto-inherited, and protected control state, while deliberately clearing `SE_DACL_AUTO_INHERIT_REQ` so the update does not request propagation to existing children. NTFS recalculates the resource-manager-owned `SE_DACL_AUTO_INHERITED` metadata when it writes the DACL. A regression starts with a protected directory DACL and verifies the stable present/defaulted/protected controls survive grant and revoke. A focused control-value test verifies that the auto-inheritance request is cleared. Another regression renames the inspected directory, creates a replacement at the original path, and verifies that the ACL change applies only to the moved original; it also confirms that the existing child DACL remains byte-for-byte unchanged. The full serial sandbox suite now contains 27 tests. Microsoft documents the handle and `WRITE_DAC` requirements for [`NtSetSecurityObject`](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntsetsecurityobject), but does not state the filesystem child-propagation behavior for this native API; only the current Windows/NTFS host has been validated. Same-user hard-link creation after the check and alias/lifetime behavior remain informational residuals, and the AppContainer remains outside the same-user process boundary.

Fresh validation on 2026-10-28 passed the same-user hard-link/path-replacement regression 1/1 and the Windows sandbox test filter 25/25. A focused rerun also passed `noninheriting_directory_acl_update_stays_on_the_inspected_handle` 1/1, confirming the ACL write remains attached to the inspected directory after path replacement. The tests reproduce the documented same-user race and confirm that current ACL behavior remains stable; they do not close the residual.

### Resolved: custom-provider edits could rebind a saved key to another endpoint

Severity: high when the renderer is compromised and a custom provider has a saved key, because the key could be sent to an attacker-controlled endpoint without being read by the renderer.

The native save command previously preserved an existing key whenever the renderer submitted a blank key, even if the provider URL or API format changed. A compromised renderer could therefore redirect a saved credential to an attacker-controlled endpoint without reading the key. The Tauri host now compares the requested destination and API format with the validated stored configuration before retaining a key. An endpoint or format change requires a replacement key; missing, malformed, or mismatched stored configuration also fails closed. The update is applied to the in-memory secret map only after validation, and persisted only after the complete update succeeds. Name-only edits and unchanged destinations preserve the key, while new providers may still omit one when the server does not require authentication. Regression tests verify rejection leaves both the previous key and configuration unchanged. Follow-up source review confirmed that the service checks the provider ID against its saved configuration, retrieves the key only for that configured route, disables automatic HTTP redirects, and bounds provider catalog response bodies.

### Reviewed: OAuth callbacks and renderer content

The ChatGPT authorization flow binds its short-lived callback listener only to `127.0.0.1`, uses a per-flow state value and an S256 PKCE verifier, bounds callback input and wait time, and exchanges the code through a fixed HTTPS token endpoint with redirects disabled. The callback reader's 1 KiB scratch buffer and accumulated request bytes use zeroizing storage. It strips query and fragment data before constructing a `Url`, then decodes callback values directly into zeroizing strings; the parsed URL therefore does not retain copies of the authorization code or state. Token response bodies are size-limited, and OpenChat-owned accumulators and token fields use zeroizing storage. Access, refresh, and ID token fields deserialize directly into zeroizing storage; the exchanged access and refresh tokens enter the zeroizing credential-pair type before ID-token validation or identity parsing, so malformed responses and later failure paths do not drop extracted credentials as ordinary strings. After copying a response chunk into its zeroizing accumulator, OpenChat attempts to zeroize the chunk when Reqwest's `Bytes` reports unique mutable ownership; it does the same before rejecting an oversized chunk. Shared, static, or externally owned chunks and any internal Reqwest/Hyper copies cannot be scrubbed by the service, so this is best-effort defense in depth rather than a complete transport-buffer guarantee. GitHub Copilot uses the fixed HTTPS device-flow endpoints, disables redirects, bounds response bodies and device-flow lifetimes, and deserializes device and bearer tokens directly into zeroizing storage. No callback forgery or token logging issue was confirmed in this pass.

The ChatGPT ID-token parser checks the issuer, audience, subject, authorized party when present, expiry, issue time, and signing algorithm header, but it does not cryptographically verify the JWT signature locally. The implementation instead relies on TLS server validation for the fixed token endpoint. OpenID Connect Core section 3.1.3.7 explicitly permits TLS server validation to validate the issuer instead of checking the signature for an ID token received directly from the Token Endpoint ([specification](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation)). This is the current trust model, not a confirmed vulnerability; its security depends on the HTTPS client's certificate validation remaining enabled.

The renderer contains no `dangerouslySetInnerHTML`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, or dynamic `eval` sink in the scanned source. Conversation Markdown is converted to React nodes; outbound Markdown and citation links are limited to HTTP(S) URLs or local fragments. Web-search attribution is parsed with `DOMParser` and reconstructed through an element allowlist, with a 32 KiB input bound and a recursion limit. This source review does not replace a rendered WebView interaction audit.

### Resolved: ChatGPT requests could replay sensitive bodies across redirects

**Severity:** Moderate cross-origin data-disclosure risk.

The shared ChatGPT HTTP client used the Reqwest default redirect policy. Reqwest removes `Authorization` when a redirect changes host, port, or scheme, but 307 and 308 responses preserve the request method and may resend its body. The shared client sends prompts and other conversation data to provider endpoints, including custom endpoints, so a redirect could disclose that body to a different origin. The client now disables automatic redirects; the existing provider error handling receives the 3xx response. A loopback regression test sends a bearer-authenticated prompt, returns a 307, and verifies the final response remains 307 instead of reaching the redirect target.

References: [Reqwest 0.13.5 redirect policy](https://docs.rs/reqwest/0.13.5/reqwest/redirect/struct.Policy.html), [Reqwest 0.13.5 redirect implementation](https://docs.rs/crate/reqwest/0.13.5/source/src/redirect.rs).

The service HTTP-client inventory was checked for the same replay path. Other redirect-following clients issue GET requests for public catalog or model downloads, or call a loopback engine health endpoint; no other prompt or conversation request body was found on a default-following client. This scoped check does not establish that unrelated SSRF paths are absent.

### Partial: workspace snapshots and failed-operation recovery (2026-10-28)

Any path matching neither checkpoint state remains a conflict and blocks writes. The 2026-10-28 file-change suite passed 44/44 with the new interrupted-restore regression. This improves retry behavior but does not make filesystem writes and SQLite commits one atomic transaction, nor prevent a concurrent same-path edit between comparison and replacement.

Workspace and single-file deltas carry the OS identity of the opened project root. Schema version 48 stores that identity with tracked changes and checkpoint files. Revert, hunk revert, approval, checkpoint restore, and failed-operation recovery require the current root to match the stored identity. Legacy identity-less records remain visible but cannot be applied. When a new delta encounters an identity-less or mismatched entry for the same path, it establishes a fresh baseline from the delta's captured before-state instead of reusing the old root's baseline. The capture path drops its handle before asynchronous tool work, so Windows root renames are not blocked by the snapshot lifetime. Windows identity also includes directory creation time. Regressions reject root replacement with matching file contents, reject identity-less checkpoint recovery, verify later tracking rebases from its current before-state, verify file and tracking rollback after checkpoint persistence fails, and verify that a multi-root manifest update rejects a mismatched later root without committing earlier-root records. Checkpoint persistence remains a separate transaction after manifest commit, so a checkpoint storage failure does not roll back already-recorded manifest entries. Tracked and hunk reverts validate the expected file snapshot before mutation, pin an existing nested parent for the operation, and use that parent capability for reads, writes, removals, and SQLite-failure compensation. Missing parents are created relative to the root and then retained through writes and compensation. If a file changes after comparison, the change may still race the atomic replacement; if compensation cannot be verified, the RPC returns a distinct rollback-failed error. Revert-all no longer suppresses individual revert errors.
